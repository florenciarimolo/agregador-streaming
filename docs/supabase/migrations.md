# Supabase Migrations Guide

This project is configured to use Supabase CLI and migrations to manage database changes.

## Initial Setup

### 1. Link the project with Supabase

First, you need to link your local project with your remote Supabase project:

```bash
npm run supabase:link
```

This will ask for:
- **Project Reference ID**: You can find it in your Supabase dashboard → Settings → General → Reference ID
- **Database Password**: The password you set when creating the project

### 2. Verify the connection

You can verify the connection status:

```bash
npm run supabase:status
```

## Working with Migrations

### Create a new migration

To create a new migration (empty SQL file):

```bash
npm run supabase:migration:new descriptive_name
```

This will create a file in `supabase/migrations/` with a timestamp and the name you provided.

**Example:**
```bash
npm run supabase:migration:new add_user_preferences_table
```

⚠️ **IMPORTANT**: All migration files MUST follow the format `YYYYMMDDHHMMSS_descriptive_name.sql` where:
- `YYYYMMDDHHMMSS` is a 14-digit timestamp (year, month, day, hour, minute, second)
- The timestamp is automatically generated by the `supabase migration new` command
- **Never manually create migration files** - always use `npm run supabase:migration:new` to ensure correct timestamp format
- When using `migration repair`, use only the timestamp number (e.g., `20260106131439`), not the full filename

### Apply migrations

#### Apply migrations to remote project

To apply all pending migrations to your remote Supabase project:

```bash
npm run supabase:db:push
```

This command:
- Compares local migrations with the remote project
- Applies only migrations that haven't been executed yet
- Is safe to run multiple times (idempotent)

#### Apply migrations in order

If you need to apply migrations one by one:

```bash
npm run supabase:migration:up
```

### Revert migrations

To revert the last applied migration:

```bash
npm run supabase:migration:down
```

⚠️ **Note**: This only works if the migration has a `down()` function defined. Most migrations don't have this by default.

### Reset local database

If you're working with local Supabase (using `supabase start`), you can reset the database:

```bash
npm run supabase:db:reset
```

This will delete all data and apply all migrations from scratch.

### Generate migration from differences

If you've made changes directly in the database (through the dashboard or SQL Editor), you can automatically generate a migration:

```bash
npm run supabase:db:diff --file migration_name
```

This will compare your remote database with the local state and generate a migration with the differences.

## Recommended Workflow

### For new database changes:

1. **Create the migration:**
   ```bash
   npm run supabase:migration:new change_description
   ```

2. **Edit the SQL file:**
   - Open the created file in `supabase/migrations/`
   - Write the necessary SQL changes
   - Make sure the SQL is idempotent when possible (use `CREATE OR REPLACE`, `IF NOT EXISTS`, etc.)

3. **Apply the migration:**
   ```bash
   npm run supabase:db:push
   ```

4. **Verify the changes:**
   - Check in the Supabase dashboard that the changes were applied correctly
   - Test your application to make sure everything works

### For existing database changes:

1. **Generate migration from differences:**
   ```bash
   npm run supabase:db:diff --file migration_name
   ```

2. **Review the generated migration:**
   - Open the generated file in `supabase/migrations/`
   - Adjust if necessary

3. **Apply the migration:**
   ```bash
   npm run supabase:db:push
   ```

## Migration Structure

Migrations are stored in `supabase/migrations/` with the format:

```
YYYYMMDDHHMMSS_descriptive_name.sql
```

Where:
- `YYYYMMDDHHMMSS` = 14-digit timestamp (year, month, day, hour, minute, second)
- `descriptive_name` = lowercase, snake_case description of the migration

**Examples:**
```
20260106131439_initial_schema.sql
20260107120000_add_user_preferences_table.sql
20260108143025_add_tagline_to_titles.sql
```

⚠️ **CRITICAL**: 
- **ALL migrations MUST have this exact format with a 14-digit timestamp**
- The timestamp is automatically generated when using `npm run supabase:migration:new`
- **Never manually create or rename migration files** - always use the CLI command
- When referencing migrations in commands like `migration repair`, use only the timestamp number (e.g., `20260106131439`), not the full filename

## Initial Migration with Existing Schema

If your Supabase database already has the schema applied (for example, you applied it manually from `schema.sql`), you have two safe options:

### Option 1: Mark the migration as applied (RECOMMENDED)

This is the fastest and safest option. It marks the migration as applied without executing it:

```bash
# First, link your project (if you haven't already)
npm run supabase:link

# Then, mark the migration as applied (use only the timestamp number, not the full filename)
npx supabase migration repair 20260106131439 --status applied
```

This tells Supabase that the migration is already applied in your remote database, without executing it.

### Option 2: Apply the migration (also safe)

The initial migration has been adjusted to be idempotent (safe to run multiple times). You can try applying it:

```bash
# First, link your project
npm run supabase:link

# Then, apply the migrations
npm run supabase:db:push
```

If something fails because it already exists, you'll see specific errors that you can ignore or handle. Most commands use `IF NOT EXISTS` or `CREATE OR REPLACE`, so it should be safe.

### Verify the status

After using either option, you can verify which migrations are applied:

```bash
npx supabase migration list --linked
```

You should see your initial migration marked as applied.

### Which option to choose?

- **Option 1 (migration repair)**: Faster, doesn't execute anything, just marks as applied. Ideal if you're 100% sure the schema matches.
- **Option 2 (db push)**: Executes the migration, but it's designed to be safe. Useful if you want to make sure everything is synchronized.

Both options are safe and **will NOT delete your data**.

## Troubleshooting

### Error: "No linked project found"

Run:
```bash
npm run supabase:link
```

### Error: "Migration already applied"

This is normal. Migrations are only applied once. If you need to reapply a migration, you must first revert it (if it has a `down()` function).

### Error: "Connection refused" or connection issues

1. Verify that your Supabase project is active
2. Verify that the credentials in `.env` are correct
3. Verify your internet connection
4. Try running `npm run supabase:status` to see the status

### Migration fails when applying

1. Check the logs in the Supabase dashboard → Logs → Postgres Logs
2. Verify that the migration SQL is valid
3. If the migration failed partially, you may need to clean up manually and try again

## Integration with Cursor

Cursor can apply migrations automatically when:

1. You have the project linked (`npm run supabase:link`)
2. Environment variables are configured correctly
3. You have permissions in the Supabase project

For Cursor to be able to apply migrations, make sure you have:
- `SUPABASE_SERVICE_ROLE_KEY` in your `.env` (for administrative operations)
- Or use the `supabase db push` command which uses the linked project credentials
